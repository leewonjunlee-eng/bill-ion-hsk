## Principles

- **The LLM does not compute amounts.** Gemini only produces "who each line belongs to", "what is on the receipt" and "a mediation proposal"; `public/core.js` computes the amounts. Model output is constrained by a schema and validated again by the server. On failure, rules are used instead and the screen labels this as rules.
- **The LLM is called only when needed.** A receipt with only one person present or only one line is split evenly without asking (`obviousAlloc`). If what would be sent to the model is the same as before, the previous answer is reused (`src/agents/cache.mjs`, server memory). The response field `how` (`obvious`, `cache`, `gemini`, `rules`) lets the screen show how the split was made.
- **An agent acts only within the range its person set.** Anything over the auto-accept limit or without evidence is always put to the owner.
- **Our service does not hold or transfer money.** Transfers happen in the user's transfer app. We only open the transfer screen, with the amount filled in, at the moment of approval.
- **Only the server writes the agent log (events).** The front end only reads it.
- **Sensitive information is handled minimally.** For location, only a summary is kept instead of the raw data; account numbers are shown only to the parties to a transfer. The store holds accounts and location summaries encrypted (`src/store/encrypted.mjs`).

## Store interface

Every method is `async`, and returned documents are copies. So changing a returned object does not change the stored one.

| Method | What it does |
| --- | --- |
| `get(col, id)` | One document, or `null`. An id that cannot be stored (not a string, contains `/` and so on) also gives `null` |
| `put(col, doc)` | Save under `doc.id` (overwrite) |
| `putIfAbsent(col, doc)` | Insert only if absent; if present, return the existing document. Concurrent calls leave only one (such as the first profile created outside the queue) |
| `delete(col, id)` | Delete a document (no error if absent or the id cannot be stored) |
| `list(col, where = {})` | Filter by field equality (same scope as Firestore `==`) |
| `roomsOf(uid)` | Rooms where `uid` is a member whose account is not deleted. `FirestoreStore` does not read every room; it reads only those rooms through the `_memberUids` index |
| `appendEvent(roomId, ev)` | Append to the agent log. Fills in `seq` (from 1 per room) and `at` (ISO time) and returns it |
| `listEvents(roomId, afterSeq = 0)` | Entries with `seq > afterSeq` |
| `eraseUser(uid)` (optional extension) | Implemented by stores that offer account deletion. Atomically deletes personal information and replaces the UID with a random anonymous one per room, and returns `{ removedLinks }`. Without it, the deletion API returns 503 and changes no data. Because it writes without the wrapper, it writes only `null`, an empty list `[]` or field deletion to encrypted fields (`SEALED_FIELDS`) (any other plaintext errors on read) |

The contract tests are in `test/store.test.mjs`. `FirestoreStore` runs the same tests when the emulator is available (`npm run test:emulators`). Things that happen only in Firestore (concurrent seq, receipt photos, the deletion transaction, security rules) are covered by `test/firestore.test.mjs`. `test/firestore-rules.test.mjs` covers whether front-end requests can see or change another room's data (list queries, members of other rooms, deletes, collections not named in the rules) (#10).

Guarantees specific to `FirestoreStore`:

- `list` order is first-insertion order (same as `MemoryStore`). For this, documents get `_order`, and `rooms` get `_memberUids` (uids of members whose accounts are not deleted) for security rules. Both are removed from returned results.
- `appendEvent` assigns `seq` by incrementing a per-room counter document (`rooms/{roomId}/meta/events`) in a transaction. If it loses a race, it throws instead of skipping a seq.
- Fields whose value is `undefined` are omitted. A `/` in an id is an error.
- `receipts` live in Cloud Storage, so `list` is not supported.

The deletion extension contract is checked by `test/account-erasure.test.mjs`. It deletes the profile, agent settings, location summaries and receipt photos the user registered or paid for, and keeps shared amounts, shares, exchange rates and event sequence numbers. An anonymized participant with `Member.deleted=true` cannot be added to new expenses. Personal information copied into split reasons, dispute evidence and event text is erased, and open mediation proposals must be checked again. No reverse mapping between the original account and anonymous UIDs is stored. QR codes already issued are invalidated and the AI response cache is cleared. A minimal `deletedUsers/{uid}` marker is kept to block access and retry deletion. Records another participant has already copied separately cannot be recalled.

Room and account APIs and tick are queued inside the server (`src/state-locks.mjs`). Work for one room waits in that room's queue, and work spanning several rooms, such as account deletion, profile changes and tick, runs alone after in-progress room work finishes. This prevents a race in which data comes back to life through deletion or revocation during an AI request. `eraseUser` and `appendEvent` in `FirestoreStore` are transactions, but read-modify-write in other APIs still relies on this queue. So Cloud Run keeps `--max-instances 1` (QR tokens, the AI cache, rate limits and the read cache in front of Firestore, `src/store/cached.mjs`, are also in server memory under the same condition). Adding instances requires moving these paths into transactions. Account deletion is not silently enabled on a store that lacks the capability.

### Encryption of account and location summary fields (`src/store/encrypted.mjs`)

`server.mjs` wraps the Store in `encryptedStore(store, key)`. Fields holding account numbers (`agents.payout`, `transfers.link`, `transfers.fallback`) and fields holding location summaries (`summary`, `leftAt`, `stayedUntil`, `nextAt` and `nextHome` in `locationEvidence`, `disputes.evidence`, which copies the summary, and `disputes.proposal`, written from the summary) are encrypted with AES-256-GCM on write (`enc:v1:…`, `src/security/seal.mjs`) and decrypted on read. So other code writes and receives plaintext, and only ciphertext stays in the store.

- An encrypted value is bound to a `collection/documentId/field` label, so it cannot be decrypted if pasted into another document. So code that changes an encrypted document's `id` must decrypt through this wrapper and insert again.
- If an encrypted field is plaintext or cannot be decrypted, an error is thrown. Encrypted fields cannot be searched with `list`.
- Empty values (`null`, empty list `[]`) are not encrypted, because account deletion (`src/store/erase-user.mjs`) empties `disputes.evidence` to `[]` without the wrapper. When adding encrypted fields, also check what account deletion writes to them.
- There is a single key, `PAYOUT_ENC_KEY` (base64, 32 bytes). The name refers to accounts, but location summaries are encrypted with it too. In deployment (`NODE_ENV=production`, set by the `Dockerfile`) the server does not start without it; locally a development key is used.
- If the real store has `eraseUser` (#2 account deletion), it is passed through, and only the links of transfers involving that person are returned decrypted (to invalidate QR tokens). Links that cannot be decrypted are skipped, since they are to be erased anyway.
- `FirestoreStore` (#3) is wrapped at the same place in `server.mjs`. However, `tick()` decrypts transfers in every room, and `sweep()`, which runs before it, decrypts disputes in rooms whose location consent has ended, so a changed key or one corrupted value stops reminders for every room. So once accounts and location summaries start accumulating in Firestore, never change `PAYOUT_ENC_KEY`.

**Why encrypt.** Article 7(2) of the "Standards for Measures to Secure Personal Information" (Personal Information Protection Commission Notice No. 2025-9) requires users' account numbers to be stored encrypted with a secure algorithm. People who register a receiving account in this service are the users meant there. AES-256 is an algorithm the Commission's guide (October 2024) gives as a recommended example. The research is summarized in a comment on PR #22. A location summary is not an account number in the sense of that provision, but it is sensitive information attached to a dispute, so it is encrypted with the same key.

- The store is currently server memory, so this encryption protects almost nothing in practice. It takes effect once accounts and location summaries start persisting in #3 Firestore. We still added it first, because encrypting after plaintext has accumulated creates a migration to re-encrypt existing values.
- Encryption in transit over the internet (paragraph 4 of the same article) is handled by HTTPS on Cloud Run and GitHub Pages. The QR code also contains not the account but a 15-minute token.
- Key management procedures (paragraph 6 of the same article) are obligations for large and mid-sized companies and public bodies with 100,000 or more data subjects, and for small businesses and organizations with 1,000,000 or more, so they do not apply at the current scale. Even so, the key is kept only in Secret Manager, pinned to version `1` and not changed.
- Authentication is protected by #2 Firebase ID token verification. Production does not accept the development identity header. Encryption does not replace authentication, and while reading with server permissions, the needed accounts and location summaries are decrypted.

## Collections and Firestore paths

The Store's `get(col, id)` and `delete(col, id)` have no `roomId`, and `tick()` scans transfers in every room. So collections are top-level, and documents that belong to a room are filtered by the `roomId` field. Only the agent log is under the room. The security rules are `firestore.rules` and `storage.rules`. **All writes are done only by the server (Admin SDK)**, and the only thing the front end reads directly is the agent log, for real-time updates.

| Collection | Document type | Firestore path | Direct front-end read (rules) |
| --- | --- | --- | --- |
| `rooms` | `Room` | `rooms/{roomId}` | Room members |
| `expenses` | `Expense` | `expenses/{expenseId}` | Room members |
| `agents` | `AgentSettings` | `agents/{uid}` | No (memories, encrypted account) |
| `invoices` | `Invoice` | `invoices/{invoiceId}` | Room members |
| `disputes` | `Dispute` | `disputes/{disputeId}` | No (the location summary is hidden only by the API's `redactDispute`) |
| `transfers` | `Transfer` | `transfers/{transferId}` | Parties to the transfer |
| `invites` | `Invite` (one per room, id = roomId) | `invites/{roomId}` | No (server only; the token is the key) |
| `receipts` | Receipt photo `{ id(=expense id), roomId, mimeType, data }` | Cloud Storage `receipts/{expenseId}` (because it can exceed the 1MiB document limit) | No (API only) |
| `users` | `UserProfile` | `users/{uid}` | The user |
| `deletedUsers` | `DeletedUser` | `deletedUsers/{uid}` | No |
| `locationConsents` | `LocationConsent` | `locationConsents/{id}` | No |
| `locationEvidence` | `LocationEvidence` | `locationEvidence/{id}` | No |
| Agent log | `AgentEvent` | `rooms/{roomId}/events/{seq}`, counter `rooms/{roomId}/meta/events` | Room members (log only, not the counter) |

Room membership is checked with `_memberUids` on the `rooms` document. Members anonymized by account deletion and members who left the room (#55, `Member.left`) are excluded from it. Members who left stay in `_leftUids`, so if they delete their account, records in the rooms they left are also anonymized.

### #7 How location evidence is judged and approved (reflects the 11/3 review)

Each of an expense's order times is converted to an absolute time on the payment date or the day before, and then the first order is chosen. Orders around midnight are not sorted as strings. Each location summary is kept for 7 days after it is attached (`LocationEvidence.expiresAt`). A summary attached later neither extends nor shortens the deadline of an earlier one. Consent (`LocationConsent`) lasts until the latest-attached summary in the room ends; expired summaries are erased one by one even if consent remains, and only the disputes that used them are reopened.

For location evidence, the server receives only the times the browser found in the Google Maps Timeline file the user chose while disputing (`public/timeline.js`). `LocationEvidence` holds only `leftAt`, `nextAt` and `nextHome`, or `stayedUntil`, plus a `summary` rebuilt by the server. It is passed to `Evidence` as `left_at` (`time`) for a leaving time, or as `text` (`stayedUntil`) if the user stayed until payment, always with `requiresHumanApproval=true`. Files, coordinates and place names are not sent to the server. Old check-in and check-out records (without `source`) are not used as evidence.

Only when the mediation model's output has `evidenceConflict` true for a line does the server cap that line's confidence at 0.49 or lower. Other lines' confidence is unchanged. The model's semantic judgment does not guarantee complete conflict detection. The rule fallback does not guess conflicts. A timeline summary is material the user submitted, so regardless of confidence it has `confirmed=false` and there is no automatic agreement. The split is finalized only after explicit agreement from both parties.

Only the parties to a dispute can read the location summary and mediation explanation through the API. Firestore rules also block direct reads of `disputes`.

## Domain type summary

For detailed fields see the JSDoc in `src/domain/types.mjs`.

- **uid:** an ASCII string (the Firebase uid since #2). The screen shows only `Member.name`.
- **Amounts and dates:** amounts are integers (KRW and JPY have no minor unit). In foreign-currency rooms, currencies such as dollars and euros accept up to 0.01 units (`decimals` in `public/currencies.js`). Dates are `YYYY-MM-DD`, times are `HH:MM`, and server schedules use `Asia/Seoul`.
- **`Room`:** has members, an exchange rate table `fx` (KRW per 100 units; base rate per payment date, card fee, per-person cash rate), the agreed exchange rate policy and a `version`. `version` increases whenever expenses change, and invoices and transfers are bound to it.
  - With `fx` it is a foreign-currency room, without it a KRW room (#55, `isForeign` in `public/core.js`). The exchange rate policy (`policy`, `policyAgreedBy`) is meaningful only in foreign-currency rooms. KRW rooms are created with `null` and `[]`, and values left in old KRW rooms are ignored on read.
  - `status`: `ready` → `settling` (after invoices are first sent) → `done` (all transfers of the current version are `confirmed`, or immediately if there is nothing to send). A finished room accepts no expenses, disputes or invites.
  - `Member.left`: a person who left or was removed. The slot remains so expense and transfer records can point to it, and they cannot read the room. Rejoining with the same invite link revives the slot.
- **`Expense`:** if `split` is `'items'`, each receipt line (`items`) is shared by the `consumers` in `alloc`. `allocMemory` is a fingerprint of the agent memories used for the split, and `allocFresh` in the room response says whether it matches the current memories (if it does, the screen blocks "split again").
- **`AgentSettings`:**
  - `memory`: memories used for settlement. The free plan allows up to 5. `memoryHidden[roomId]` lists memories whose sharing is turned off in that room; by default all are shared. Memories going to the model pass through `sharedMemory()`.
  - Visibility: what is used for settlement and what others see are different. Only the user sees memory text and the auto-accept limit amount. Split reasons are rewritten by code from who each share belongs to, instead of text written by the model or rules (`publicReason`), and invoice reasons and the agent log do not include the limit amount. Memories can be quoted as evidence only in dispute mediation.
  - `rules`: auto-accept limit, send timing (`'manual'` when convenient, `{ payday: 25 }` that day each month; the old `'now'` is read as `'manual'`), dispute handling and notification level (`'actions'`, `'all'`). This is one set of defaults per person ("My agent defaults" in My account), used in every room. If `roomRules[roomId]` has values set only for that room (auto-accept limit, send timing, dispute handling), only those fields override (`rulesIn()`). The old `rulesOff` is migrated on read into room-specific safe values. A `'manual'` transfer has `manual: true`, and the sender is notified once only if the recipient has not said it was received by 09:00 KST 3 days later. A corrupted value is read as the default, so the limit becomes 0; that is, every invoice is asked about.
  - `ruleHistory`: rule change history (last 50). `onboardedAt`: when first-time setup was completed.
  - `payout`: the receiving account. One per person; changing it updates the pending transfer links in every room where that person will receive.
- **`AgentEvent.action`:** something a person has to do. `type` is one of `confirm_line`, `answer_invoice`, `agree_dispute`, `approve_transfer`, `confirm_receipt`, `set_payout`, and `for` is the person who has to do it.

| POST | `/api/rooms/:id/disputes/:did/revise` | Revise a mediation proposal `{ alloc: { [itemId]: [uid, ...] }, rev? }`. A party changes the people per line and proposes again. The revised proposal has `proposal.source` `'human'` with `revisedBy` and `rev`; only the reviser counts as agreeing (`agreedBy`), and the other side is asked again (`dispute_revised` entry, `agree_dispute` to-do). Parties only (otherwise 403), only while the proposal is live and the revision matches (otherwise 409). Every line must belong to that expense and each line needs at least one person who was present (`present`); if no line changed or anything is wrong, nothing changes (400) |
| POST | `/api/rooms/:id/disputes/:did/reject` | Reject a mediation proposal `{ reason? }` (one line, up to 100 characters). The dispute ends (`withdrawn` if the person who raised it rejects, `dismissed` if the person who paid rejects), and settlement continues with the expense split as it is. Parties only (otherwise 403), only when there is a proposal (otherwise 409). If the same person sends it again, the first result is returned |
| POST | `/api/rooms/:id/payout` | Receiving account `{ bank, accountNo, holder }`. Fills Toss links into pending transfers in every room where I will receive. Since it changes several rooms, it waits in every room's queue (`src/state-locks.mjs`) |
| POST | `/api/me/payout` | Receiving account set in My account's agent defaults `{ bank, accountNo, holder }`. Set without a room; only rooms with pending transfers are notified. Waits in every room's queue |

Only the last 4 digits of the account number are returned (`payout.last4`). `myAgent` in the room response is a summary that only says whether there is an account. `agentReady` in the room response lists uids of members who finished agent setup; the screen shows it only as a robot mark next to the name (no rules or memories) |
| POST | `/api/me/agent/rules` | Some rules `{ autoAccept?, sendWhen?, onDispute?, notify? }`. Only changed fields go into `ruleHistory`. Applied from the next invoice; invoices and transfers already created are unchanged |
| POST | `/api/me/agent/onboarding` | Finish first-time setup `{ rules? }` |
| POST | `/api/me/agent/memory` · `memory/edit` · `memory/delete` | Add a memory `{ text }`, edit `{ from, to }`, delete `{ text }`. 409 over the limit |
| POST | `/api/rooms/:id/agent/rules` | Rules for this room only `{ autoAccept?, sendWhen?, onDispute? }` (room members only). Giving a value sets that field; `null` clears it so the default applies. The notification level is not split per room. `myAgent` in the room response gives the values actually used in this room, the fields set here (`custom`) and the defaults (`defaults`). It changes the one agent document per person, so it waits in every room's queue |

**Dispute states** go from `open` (a dispute arrived) → `proposed` (a mediation proposal is out) and end in one of three ways. While `proposed`, a party can change the people per line and propose again (`revise`); the state stays `proposed` and waits for the other side's agreement again. If both agree, `resolved` (the expense is split as proposed, the version increases and invoices are sent again); if a party rejects, `withdrawn` or `dismissed` (expense and version unchanged); if the expense changes, `superseded`. No transfers are created while any dispute is open (`open`, `proposed`), so it must end one way or another or the room stalls. If an expense's split changes (edit via `POST /expenses/:eid`, line confirmation, redoing the menu split, deleting the expense), its open disputes are closed as `superseded` with a `dispute_superseded` entry (`src/agents/disputes.mjs`). Edits that don't change shares (title, kind, payment time) leave disputes alone. For an expense whose dispute was resolved by agreement, ended by rejection or closed because the expense changed, the agent does not dispute again on the same evidence in the next version's invoices (since a person edited the expense directly, it is considered settled).

`actions` are not counted from the event log; the server computes them from the current state (`src/actions.mjs`). So handled items drop out automatically. The kinds are `confirm_line` (confirm a line), `answer_invoice` (invoice over the limit), `agree_dispute` (hand to mediation, accept a proposal), `approve_transfer` (a due transfer, or one where you are asked again whether you sent it), `set_payout` (no receiving account) and `confirm_receipt` (confirm receipt).

**Transfer links are created in advance.** A browser opens an app only within a user gesture. So when a transfer is created, the server fills in `link` (Toss transfer screen) and `fallback` (for copying account and amount), and the screen opens the link the moment the slider is released.

## Run locally

```bash
npm start                      # Home screen and demo: http://localhost:4500
DEV_SEED=1 npm start           # To open the real room screen with seed data
npm test                       # Contract and calculation tests (tests that need an emulator are skipped)
npm run test:emulators         # Starts the Firebase emulators (Firestore, Storage, Auth) and runs all tests. Needs Java 21 and firebase-tools
```

To start the server with Firestore, see the [Firestore guide](docs/firestore-setup.md).

Without a key it runs in rule mode. If you need Gemini, put `GEMINI_API_KEY` in `.env` (`.env` is not committed to the repository).
